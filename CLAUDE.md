# Keyboard Sensei — Project Status

Full-stack piano learning web app. pnpm monorepo: `apps/web` (React/Vite/TS/Tailwind/VexFlow/Zustand), `apps/api` (Express 5/Prisma/PostgreSQL/JWT/Zod), `packages/{shared-types,midi-engine,music-theory,lesson-engine}`. See `README.md` for local setup commands.

**Collaboration pattern:** detailed written spec → Codex background job (`node <codex-companion.mjs path> task --background --write --fresh "<prompt>"`, found via `codex:setup`) for backend/content work → Claude verifies live (real Postgres + browser), never trusts Codex's own "typecheck/tests passed" as sufficient — its sandbox has no Docker/Postgres/network, so it cannot do real E2E verification itself.

There is also a stale early-prototype copy at the parent directory root (`../apps/web` only, no api, no git repo, frozen ~2026-07-01) — not this project, safe to ignore or delete after confirming with Ramin.

### Deploy
Live on the home LAN server at `192.168.4.4` (Debian, user `ramin`), Dockerized, reachable at `https://192.168.4.4:8181` (Caddy reverse proxy) / `:3101` (api), via Tailscale subnet routing when off-LAN. HTTPS only (internal CA) — required for Web MIDI hardware input, which browsers only allow in a secure context. Each LAN device that wants hardware MIDI needs the Caddy CA root imported once (copy from `/data/caddy/pki/authorities/local/root.crt` inside the `keyboard-sensei-caddy-1` container, or from the shared drive at `/home/ramin/shared/keyboard-sensei-lan-ca.crt`) — `security add-trusted-cert -d -r trustRoot -k ~/Library/Keychains/login.keychain-db <path>` on macOS, then fully quit and reopen the browser (a tab refresh alone won't pick up newly-trusted certs).

**ALWAYS deploy from a clean worktree at HEAD, never the working tree.** Agents frequently have uncommitted work in flight, and rsyncing the working tree ships it. A broken deploy was caused exactly this way (a file staged while an agent was mid-edit, importing a module that wasn't committed yet).

```sh
git worktree add --detach /tmp/ks-deploy HEAD
cd /tmp/ks-deploy
rsync -az --exclude 'node_modules' --exclude '.git' --exclude 'dist' --exclude '.pnpm-store' \
  --exclude '*.log' --exclude '.env' --exclude 'apps/api/.env' --exclude 'apps/web/.env' \
  --exclude '*.tsbuildinfo' --exclude '.env.deploy' --exclude 'apps/api/data' \
  ./ ramin@192.168.4.4:~/apps/keyboard-sensei/
ssh ramin@192.168.4.4 "cd ~/apps/keyboard-sensei && docker compose --env-file .env.deploy -f docker-compose.deploy.yml up -d --build"
cd - && git worktree remove --force /tmp/ks-deploy
```

## Gotchas / Lessons Learned

| Issue | Cause | Prevention now in place |
|---|---|---|
| VexFlow sharp/flat glyphs positioned but never drawn | `Accidental` modifiers computed but never attached to the `StaveNote` | Content verification cross-checks MIDI note numbers against the *rendered* VexFlow output, not just theory — invisible bugs like this don't show up from note-number review alone |
| Accidentals clipped off-canvas on long note runs | Canvas width was a fixed 420px; a note late in a run formatted past the SVG edge | Width scales with note count (`computeStaveWidth` in `NotationRenderer.tsx`) |
| Stale hardcoded lesson-count strings (e.g. "12 lessons") | UI strings weren't made count-agnostic when content volume grew | Grep for hardcoded counts whenever content volume changes |
| CORS port mismatch; a logout state bug | — | Caught pre-ship by live verification, not static checks |
| **Structural:** Codex's own "tests passed" report is never sufficient | Its sandbox has no Docker/Postgres/network | Claude always verifies live (real Postgres + browser) before accepting Codex's work as done — every bug above was invisible to static checks alone |
| Custom response headers (`x-song-*`) invisible to the browser cross-origin | `cors()` had no `exposedHeaders` — custom headers aren't CORS-safelisted by default; `curl` (which ignores CORS) can't catch this, only a real browser fetch can | Any new custom response header a client reads via `response.headers.get(...)` must be added to `apps/api/src/app.ts`'s `cors({ exposedHeaders: [...] })` list |
| Adding a new npm dependency broke unrelated existing code's typecheck (`NotationRenderer.tsx`'s `vexflow` imports) | `opensheetmusicdisplay` transitively depends on old `vexflow@1.x` + `@types/vexflow`; that package's `declare module "vexflow"` ambient block is global once loaded anywhere in the TS program, not scoped to the file that needed it — it shadowed this app's own real `vexflow@4.x` types everywhere | `apps/web/tsconfig.json` now has an explicit `"types": [...]` whitelist (prevents automatic `@types/*` pollution from any future transitive dependency); the one existing conflict was neutralized via `pnpm patch` (see `patches/@types__vexflow@1.2.42.patch`) |
| A "prevent duplicate work" `useRef` guard silently broke a `useEffect` under React 18 StrictMode | Dev-mode double-invoke (mount→cleanup→mount): the first throwaway mount set the ref before its cleanup ran, so the real second mount's guard saw it "already done" and skipped — no error, just silently broken (`OsmdNotation.tsx`, notation stayed blank) | Don't add a manual "already ran" ref check on top of a `useEffect`'s own dependency array unless you've specifically verified it survives StrictMode's double-invoke; the dependency array alone is usually sufficient |
| `scrollIntoView({behavior:"smooth"})` called on a fast-updating interval (~120ms) never visibly moved the page | Each call interrupted/restarted the previous animation before it could progress — `scrollY` stayed pinned even though the call fired correctly every time | Use `behavior:"auto"` (instant) for any auto-follow-scroll driven by a frequently-updating value; verify with a real timed live check (`window.scrollY` before/after), not just confirming the function was called |
| Highlighting a note re-rendered the ENTIRE score | `NotationRenderer`'s draw effect had `activeNoteIds` in its dependency array, so every change to the sounding note re-formatted and re-drew all of VexFlow. On the scrolling score that's the whole piece (47,258px wide, 3065 notes on the largest song) — redrawn once per note. Visible as stutter/jank, not as an error | Highlighting is **styling, not content**: draw once, then toggle a CSS class on the already-rendered SVG elements. Never put a high-frequency prop in a render effect's deps |
| A MIDI note-on is **not** a user gesture | The AudioContext created by the note handler stayed suspended and its `resume()` was silently ignored by the browser. A hardware keyboard lit up the on-screen keys but made **no sound** until you clicked something (e.g. Play) — after which it worked forever, which made it look like a play/stop bug | `apps/web/src/utils/audioUnlock.ts`: every AudioContext registers, and the first real pointer/key/touch event resumes them all |
| Time-signature **denominator** silently discarded | `playalongSong.ts` read `timeSignatures[0].timeSignature[0]` (numerator only) and everything downstream assumed a beat == a quarter note. 6/8 bars came out **2× too long**, 2/2 **2× too short** — 47 of 311 library files were wrong, including a Chopin nocturne off by 43s by bar 8. Nobody reported it | Bar length in quarter notes = `numerator * (4 / denominator)`. 15 files also change meter mid-piece, so `beatsPerBar` is **not a scalar** — walk `timeSignatureSegments` |
| Beat/bar grids built from `tempos[0]` drift within 1–2 bars | 31 of 311 library files have a real tempo map. A grid pinned to the first tempo event goes >1 bar wrong on Coldplay/Queen tracks | Build the grid with the **same** `header.ticksToSeconds()` that already places the notes. Same coordinate system by construction — drift becomes impossible, not merely bounded |
| `xFor()` returned `x = 0` for out-of-range notes | `whiteIndex.get(note) ?? 0` — every note outside the keyboard silently drew stacked on the lowest key, and was unplayable, so the score collapsed with no visible cause | Returns `null`; callers skip. Play-Along sizes its keyboard to `union(deviceRange, songRange)` so it never fires |
| Canvas reallocated every frame at 60fps | `canvas.width` is an **integer** setter, but fit-to-width makes `geometry.widthPx` fractional, so `canvas.width !== widthPx * dpr` was *never* equal | Round both sides before comparing |
| CI was red for months, unnoticed | Two independent causes: (1) `apps/api/src/config.ts` validates env with Zod **at import time**, and CI sets no `DATABASE_URL`/`JWT_SECRET`/`ELEVENLABS_API_KEY`, so importing anything that reached it threw before a single test ran; (2) web tests read MIDI fixtures from the **gitignored** `apps/api/data/midi-library` | `apps/api/vitest.setup.ts` supplies dummy env. `libraryFixtures.ts` probes for a **specific** seeded file — note `apps/api`'s own upload tests *write* `.mid` files into that same dir, so "does the folder exist" and "does it contain any .mid" both give false positives |
| `apps/web/vite.config.js` was a stale **compiled** artifact | Committed in the initial commit. Vite resolves `.js` **before** `.ts`, so every build silently used the transpiled file while `vite.config.ts` sat there looking authoritative | Deleted. If you add a Vite plugin, edit `vite.config.ts` and confirm no `.js` twin exists |
| A test can pass for the wrong reason | A rubato test used a Coldplay excerpt whose tempo happened to be locally constant, so naive and correct methods agreed and the test went green while proving nothing | Pick fixtures that actually exercise the thing (Clair de Lune for rubato). A green test that proves nothing is worse than no test |

- **Metronome: continuous tempo + scoring — scoped and reviewed 2026-07-12, ready to build.** See `docs/superpowers/specs/2026-07-12-adaptive-keyboard-design.md` and the Opus design review's conclusions, summarised here.

  **CORRECTION to what this roadmap used to say:** it claimed the four `*_CONFIG` objects in `packages/midi-engine/src/config.ts` were per-tempo tolerance tiers to interpolate between. **That was false.** They are *difficulty presets* (beginner/elementary/intermediate/advanced), spread into each authored exercise at content-definition time (`apps/api/src/content/helpers.ts`), and are never keyed by tempo. `scoring.ts` reads `exercise.timingToleranceMs` and nothing else; tolerance does not scale with tempo today at all. (`ADVANCED_CONFIG` is dead — referenced by zero content.) Do not try to interpolate between them.

  Agreed design:
  - **Internal unit is `rate`, not BPM.** `playalongEngine.ts` is already a playback rate (`tempoPct / 100`).
  - **BPM only where it's real:** lessons/Practice Gym have an authored `MidiExercise.tempoBpm`, so they get the true 25–200 BPM slider. **Play-Along has no reliable base BPM** — `Song` has no bpm column, and BPM is derived client-side as `midi.header.tempos[0]?.bpm ?? 120`, which is a fiction for the rubato/tempo-curve performance MIDIs that make up the library. Play-Along therefore gets a continuous **%** speed control, with a BPM hint only when the MIDI has a single stable tempo. Its metronome clicks follow the song's own beat grid (from the tempo map × rate), so it stays in sync even with rubato.
  - **Tolerance scales with the beat, anchored so `rate = 1` is a no-op:** `clamp(exercise.timingToleranceMs * rate^-0.5, 60, 400)` — identical scores at default tempo, so all 34 lessons and all existing history stay comparable. Same for `simultaneityWindowMs`. `durationTolerancePercent` is already a percentage of a tempo-scaled duration, so leave it alone.
  - **Multipliers:** `tempoMultiplier = sqrt(rate)` (the existing `{25:0.5, 50:0.7, 75:0.85, 100:1}` table is a rounded √). `lookaheadMultiplier = clamp(1 + 0.21*ln(4 / lookaheadS), 0.85, 1.30)` (fits the existing 4 tiers). **Cap the product at 1.5** and raise the API `score` cap (`songs.ts`, currently `max(150)`) to 160 — otherwise fast runs produce scores >150 and Zod rejects the attempt, so the user's best runs are the ones that fail to save. Retune `gradeFor`.
  - **DB migration (safe, no backfill):** `ALTER COLUMN tempo_pct TYPE DOUBLE PRECISION` (in-place, lossless — existing 25/50/75/100 rows survive) and `ADD COLUMN tempo_bpm DOUBLE PRECISION NULL` for display. **Never backfill `tempo_pct × base_bpm`** — there is no trustworthy base BPM to multiply by.
- **MIDI hardware note-range issue reported on Ramin's Mac (2026-07-12), likely NOT a Keyboard Sensei bug — not investigated further, flag if it resurfaces.** Reported as notes below a certain pitch (initially said G5/D5, corrected to G3/F3) not registering during physical MIDI keyboard input.
